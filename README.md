# Dandelion Dashboard

Dandelion is a terminal dashboard that shows how much of your AI allowances you have left: subscription usage windows for `claude`, `agy`, `kimi`, `grok`, `codex` and `cursor`, the credits balance for `junie`, the Nous Portal credits for `hermes`, and the API balance for `kilo`.

Called dandelion because dandelion seeds can lay dormant for a period of time before bursting into life. It's why they're such a prolific weed. But anyway this fits the naming convention I started with marestail and also it's sort of similar to you'll use up a session window for an llm then it will come back lol.

Pace warning: when a window of known length (rolling `5h` windows, and windows whose label contains `week`, which are 7 days) is on course to hit 100% before it resets, a dim line `  → 100% in ~1h20m (before reset)` appears directly under its row, in the live dashboard and in `--once`. The projection assumes the usage so far was spread evenly over the time elapsed in the window, and stays silent for windows of unknown length, a missing or past reset, 0% or full usage, and windows under 5% elapsed. Routing and `route` output are unaffected.

Usage sparkline: in the live dashboard's full view, a window row with at least 2 `history.json` samples (see Usage history) for the same provider, window position and label in the last 24 hours shows a dim 8-cell sparkline between its percent and its reset countdown. Each cell is one 3-hour bucket of those 24 hours, oldest on the left, showing the newest sample in the bucket from `▁` (0%) to `█` (100%) in eight steps; a bucket without samples is a space. Under `NO_COLOR` the cells are ASCII, `_` `.` `-` `=` `#` from 0% to 100%. The sparkline takes 9 cells from the gauge and is the first thing dropped when the terminal is too narrow for it (the gauge would fall under 6 cells), before any label or countdown is cut. `--once`, the compact view, `--json`, `--line`, `--waybar` and the `g` graph are unchanged.

Pace marker: on those same windows of known length with a reset in the future and no further away than the window length, the gauge shows a dim `│` (`|` under `NO_COLOR`) at the point where steady usage would be, that is the share of the window already elapsed, in the live dashboard and in `--once`. The marker replaces the cell at that position and the gauge keeps its width, so a fill past the marker means you are ahead of pace. Windows of unknown length, a missing or past reset, a reset further away than the window length, and balance rows get no marker.

## Providers

Panels always appear in this order. A provider whose CLI is missing, fails, times out or prints unexpected output renders as a dim panel with the reason; a probe that crashes unexpectedly renders as a failed panel with the fixed reason `probe crashed` (the error message is never shown) and routes as failed; when claude, agy or kilo exits with an error, the reason is `Command exited with an error: ` and the first line the CLI wrote to stderr (stripped of control characters, with long secrets replaced by `…`).

- `claude` (claude · personal) - runs `claude -p "/usage"` (90s timeout) and shows the session, weekly and per-model weekly windows with a reset countdown. In the live dashboard it also shows `status: <description>` under the header while status.claude.com reports an incident (see `DANDELION_CLAUDE_STATUS_URL`).
- `claude-work` (claude · work) - runs the same command with `CLAUDE_CONFIG_DIR` set to the work config dir and shows the same windows for the work account, with the same live `status:` line. Without that dir it is unavailable and never runs claude.
- `claude-animus` (claude · animus) - runs the same command with `CLAUDE_CONFIG_DIR` set to the animus config dir and shows the same windows for the Animus account, with the same live `status:` line. Without that dir it is unavailable and never runs claude.
- `claude-deepseek` (claude · deepseek) - reads `ANTHROPIC_AUTH_TOKEN` from `<config dir>/settings.json` and GETs `https://openrouter.ai/api/v1/key` (10s timeout) for the key's spending limit and what remains of it, then `https://openrouter.ai/api/v1/credits` (10s timeout) for the account's balance, `total_credits` minus `total_usage` and never below zero. The window is the key's limit with what is left capped at that balance, because a key with limit to spare still fails with HTTP 402 once the account is empty. The window counts as weekly, so it joins headroom and never trips at 90%. The plan label is the reset period, the dollars the key has left and the balance, such as `monthly · $20.00 of $20.00 · balance $35.00`. A null limit says `openrouter key has no spending limit` and skips the credits request; a failed credits request reads like a failed key request, such as `openrouter credits request failed: HTTP 403`. Without the dir or a token the panel says `no deepseek config — CLAUDE_CONFIG_DIR=~/.claude-deepseek claude`. The token and the response body are never printed. The live dashboard shows the same `status:` line under its header.
- `claude-ollama` (claude · ollama) - Claude Code on Ollama Cloud. Reads the ollama.com login cookie from `<config dir>/ollama-session` (the value of the `__Secure-session` cookie, with or without the `__Secure-session=` prefix) and GETs `https://ollama.com/settings` with it (10s timeout) for the plan's session and weekly usage. The `session` window is rolling, so it trips at 90%, and the `weekly` window joins headroom and evaporation; each takes its reset from the page. The API key in `settings.json` cannot read these numbers, which is why the probe needs the browser session. Without the config dir the panel says `no ollama config — CLAUDE_CONFIG_DIR=~/.claude-ollama claude`, without the cookie file `no ollama.com session — save __Secure-session in ollama-session`, and when ollama.com answers with its sign-in page `ollama.com session expired — replace ollama-session`. The cookie and the page are never printed.
- `agy` - runs `agy -p "/usage"` (60s timeout) and shows each model group's windows; agy reports remaining percent, shown as used percent.
- `kimi` (kimi code) - reads the OAuth access token from `~/.kimi-code` (`config.toml` for `base_url` and the credential `key`, read from the `[providers."managed:kimi-code"]` table (the key also from its `.oauth` sub-table, where kimi writes it), or from the top-level keys before the first table when that table is absent, never from another provider's table, then `credentials/`) and GETs `{base}/usages` (10s request timeout). The token is never printed or written. With a valid token, on the legacy plan the weekly window is `usage` used/limit and the rolling `5h` window is the 300-minute `limits` detail, so a `used_ratio` stuck at 0 does not hide real usage. With an expired token and a `refresh_token`, kimi refreshes it itself. Dandelion starts `kimi web --no-open --port <port>`, polls the credential file every 500ms for up to 20s (an unreadable file mid-write counts as not fresh yet), stops the server, then calls the coding API as above. kimi web's own `/api/v1/oauth/usage` only exposes the zeroed ratios, so it is not used for this. Dandelion never writes kimi's credential file and never calls the refresh endpoint, because refresh tokens may rotate and would break kimi's own login. If the refresh fails (kimi exited, the port was taken or 20s passed) it says `kimi token expired and kimi web did not refresh it — run kimi once`. Without a `refresh_token`, or with `kimi` not installed, it says `kimi token expired — run kimi once`. With no credential file it starts `kimi web --no-open --port <port>`, waits up to 20s for the token it prints, and reads `kimi web`'s local usage endpoint `/api/v1/oauth/usage` (10s request timeout), then shuts the server down with SIGTERM, then SIGKILL after 5s. It shows the weekly window and the rolling `5h` window, each with a reset countdown.
- `grok` - GETs `https://cli-chat-proxy.grok.com/v1/billing?format=credits` with the bearer token from `<grok home>/auth.json` (10s timeout; the token is never printed). A 401 runs `grok models` once (20s) to refresh the login and retries the request once. A response whose current period carries no usage percent counts as 0% used, because the API leaves the field out when nothing has been used. When that request fails, or the response has no period and no usage percent, it reads the newest billing snapshot from `<grok home>/logs/unified.jsonl` without running grok, and shows the credits window with a reset countdown, the subscription tier and the snapshot's age. A snapshot older than 48h is shown dim as stale. When the snapshot's billing period has already ended, grok has reset its credits, so the window shows 0% with no reset countdown and the caption ends with `· period ended since snapshot`; routing then sees grok as unused. Without a snapshot the panel says to run grok once.
- `codex` - runs `codex login status` (15s timeout). Logged in with an API key, it shows "api-key billing · no usage windows", because API usage has no windows. Logged in with ChatGPT, it starts `codex app-server` and reads `account/rateLimits/read` over JSON-RPC on stdio (30s timeout), then shows the primary and secondary windows with a reset countdown. The server is then shut down with SIGTERM, then SIGKILL after 5s. In the live dashboard it also shows `status: <description>` under the header while status.openai.com reports an incident (see `DANDELION_OPENAI_STATUS_URL`).
- `codex-animus` (codex · animus) - runs the same `codex login status` and `codex app-server` probe with `CODEX_HOME` set to the animus home (`DANDELION_CODEX_ANIMUS_HOME`, default `~/.codex-animus`) and shows that account's windows, with the same live `status:` line. When the home is not a directory the panel says `no animus codex home — CODEX_HOME=~/.codex-animus codex login` and never runs codex.
- `cursor` - reads the access token from the cursor-agent auth file without running cursor-agent, and POSTs to the dashboard API's `GetCurrentPeriodUsage` and `GetPlanInfo` (15s timeout each) to show the total, auto and api windows with a reset countdown and the plan name and price. The token is never printed or written. In the live dashboard it also shows `status: <description>` under the header while status.cursor.com reports an incident (see `DANDELION_CURSOR_STATUS_URL`).
- `junie` - reads the current JetBrains balance from the same `/auth/test` account endpoint Junie uses. It reads the existing OAuth login from `<junie home>/secure_credentials.json`, refreshes an access token in memory, and makes a quota request without starting an agent or writing credentials. A live balance of zero shows `0 credits` and 100% used and is never routed; a later replenishment is picked up automatically. A failed live request makes Junie unavailable rather than falling back to an older successful balance. Without a readable stored OAuth login, it supports the legacy completion snapshots in `<junie home>/sessions/<id>/events.jsonl`, visiting `<junie home>/sessions/index.jsonl` newest first; these show the snapshot's actual age and are dim when older than 48h. Without either source the panel says to run junie once.
- `hermes` - reads the Nous Portal tokens from the hermes auth file without running hermes, GETs `/api/oauth/account` (15s timeout) for the credits window with a reset countdown and remaining versus the monthly grant, and never prints the tokens. Without a token the panel says to run `hermes portal login`; when the token is expired it says to run `hermes once`.
- `kilo` (api balance) - runs `kilo profile --json` (20s timeout), reads only the balance and its currency, and shows a balance such as `balance $31.23` without exposing personal profile fields. The balance is not a usage window: the panel does not invent a usage percentage, gauge or reset time.

Final live verification reported `31.232105 USD`; the quota UI rendered `balance $31.23` exactly once with no synthetic gauge, and Kilo stayed visible in `usage only` with zero windows. The dashboard API normalizes literal `$` to `USD` before rendering. `marestail gate` and all 23 QA modules passed.

All fourteen probes run in parallel. Window gauges are coloured by usage: below 50% calm, 50-79% warm, 80-94% hot, 95% and above critical.

## Run Commands

- `npm start` - Run the live dashboard: panels fill in as each probe settles, a fleet summary line shows how many windows are at 80% or more and the next reset, and everything is re-probed every `DANDELION_REFRESH_SECONDS`, or at once when the dashboard notices its data is older than that (for example after the machine wakes from suspend). Each settled panel's caption ends with its data age, such as `claude · personal · 3m ago`, and while a panel is being re-probed it keeps showing its previous numbers with a spinner after the provider name; only a panel that has never settled shows `probing…`. At start, every provider whose entry in `snapshot.json` has status ok and was fetched at most 24 hours ago is drawn at once as if it were being re-probed (its stored rows, a spinner and a caption ending in the age of that entry, such as `· 7m ago`) instead of `probing…`; until the first round settles that data counts as not settled for everything else (route boxes still probing, `c`/`C` and `l`/`L` flash `nothing to copy` / `nothing to launch`, no notification baseline, no history sample, no snapshot write, `s` sorts it as probing, `x`, `space` and `R` act as on a pending panel), each panel switches to live data when its own probe settles, and a missing or unreadable `snapshot.json` or a `DANDELION_DISABLE`d provider starts as before. When a re-probe of a provider that last settled ok comes back unavailable or failed, its panel keeps showing the last good rows (or balance line) dimmed and uncoloured, followed by `last probe failed: <reason>`, and its caption ends with the age of that good data (`· 7m ago`) until the provider settles ok again; the route boxes, `c`/`C`, notifications and the history still treat it as failed, exactly as `dandelion route` would, and a provider that has never settled ok shows its failure as before. Two boxes at the top show the answers `dandelion route` and `dandelion route --high` would print; they update when a round settles or routing is toggled. The frame fits the terminal: the `route` and `route --high` boxes stay at the top, and the provider list scrolls with `↑↓/jk` so earlier panels, personal `claude` included, stay reachable. The list shows every panel from the first when they all fit, and otherwise scrolls only as far as needed to keep the whole selected panel in view (from its header when it is taller than the list). The frame also fits the terminal's width: the banner, dividers and the two route boxes span the full width, the gauges grow (up to 80 cells) so the percent and reset columns sit near the right edge, and a narrower terminal shrinks the gauges and labels, cutting lines only as a last resort (never mid-escape, always closing the style); a resize redraws at the new width, and without a usable width the layout is the fixed 72 columns (`--once` is always 72). Keys: `↑↓/jk select` a panel, `space routing on/off` for the selected provider, `h hide` the selected panel, `H show hidden` panels, `g` a full-screen usage-over-time graph of the selected provider (first panel if none is selected; `esc`, `q` or `g` goes back), listed in the `?` help as `g usage graph of the selected panel · esc/q/g back · v compact · w why` above the keys line, `r` refresh everything, `R` or `enter` re-probe only the selected panel's provider (nothing happens without a selection, while a round or that panel's own probe is running; the refresh timer is not reset; a provider is also re-probed on its own, without a key press, once a reset time it reported is at least 60s in the past, using the same single-panel re-probe (spinner, previous rows kept, route boxes recomputed when it settles), at most once per provider per passed reset value for the session, and never while a round or that panel's own probe is running, so the panel and the routes do not keep a window that has already reset at its old percent), `c` copy the `route` line and `C` the `route --high` line to the clipboard (`wl-copy`, else `xclip -selection clipboard`, else an OSC 52 sequence written to the terminal) with a 2s `copied: <line>` flash in place of the summary line (`nothing to copy` while probing, when the answer is `none` or routes.json is bad; `copy failed` when every method fails), `x` run the selected panel's suggested fix command (`hermes portal login`, `hermes once`, `cursor-agent login`, `claude` with `CLAUDE_CONFIG_DIR` set to the work config dir or to the deepseek config dir, `codex login` with `CODEX_HOME` set to the animus home, `kimi` when its token has expired, `grok` or `junie` when there is no snapshot or it is stale) in the foreground: dandelion leaves the alternate screen and raw mode, runs it with inherited stdio, Ctrl-C inside the fix command ends only that command and returns to the dashboard (dandelion ignores SIGINT while it runs), no scheduled refresh, automatic re-probe or notification starts while it runs (notifications that came due meanwhile are sent after it exits, not dropped), and when it exits restores the screen, redraws and starts a full refresh round unless one is running; panels with a fix end their caption with `· x fix`, `x` on a panel without one flashes `no fix for this panel`, and nothing happens without a selection (the hint and key exist only in the live dashboard; `--once`, `route` and `--json` are unchanged and no token is ever passed on the command line), `l` launch the line shown in the `route` box and `L` the line in the `route --high` box: the command is built exactly as `dandelion run` builds it (`claude-work`, `claude-deepseek` and `claude-ollama` set `CLAUDE_CONFIG_DIR`, `codex-animus` sets `CODEX_HOME`, model and effort passed through, no extra arguments) and runs in the foreground like `x` (alternate screen and raw mode left, SIGINT ignored by dandelion while it runs, no refresh, re-probe or notification meanwhile, and notifications held back meanwhile are sent after it exits; on exit the screen is restored and a full refresh round starts), `nothing to launch` is flashed while probing, when the answer is `none` or routes.json is bad, and `<command>: command not found` when the CLI is not on PATH; the `?` help lists it as `l/L launch`, `s` cycle the panel order (`dashboard`, `headroom`, `reset`), `t` reset times, `v` toggle a compact view, `q` quit (or Ctrl-C), `?` help. `t` switches every reset countdown and the summary line between relative (`↻ 4d3h`, the default) and absolute local time (`↻ Sat 21:40`, or `↻ Oct 12 21:40` when the reset is 6 or more days away); the mode is saved in `view.json` (see below) and `--once` always shows countdowns. `s` cycles the order of the panels: the fixed dashboard order, then most headroom first (100 minus the highest used percent over a panel's windows), then soonest future reset first; panels without windows or a future reset, and panels still probing, come last in dashboard order, and ties keep dashboard order. The order is recomputed as results settle, the selection stays on the same provider, the summary line ends with `· sort: headroom` or `· sort: reset` while a non-dashboard order is active, and the order is saved in `view.json` (see below). Route boxes, `route` and the eligibility state file do not depend on it. The `?` help lists it as `s sort` on its first line. `w` shows under each route box the lines `dandelion route --why` and `dandelion route --high --why` would print after the route line, for the dashboard's current results, eligibility and clock (recomputed whenever the boxes are; nothing is shown while a round is probing or when routes.json is bad), stacked (route lines, then route --high lines) and cut to the frame width; the provider list gets fewer rows so the frame still fits, `w` again hides them, and the toggle is for the session only (not saved in `view.json`). `v` switches the provider list to one line per provider: the name with the `▸ ` selection marker, a 20-cell gauge and percent for the window with the highest usage (rolling and weekly windows first, else any window), and `↻` the soonest reset among its windows, coloured like the full view. Providers without windows show their note, balance or reason dim, pending ones show the spinner, ineligible ones `routing off`, and the selected row is bold; rows are cut to the frame width. The banner, summary line and route boxes stay the same, every other key works as before, and the view is not saved.
- Signals: while the live dashboard runs, SIGTERM and SIGHUP (`kill <pid>`, a closed tmux pane, a session manager) do what `q` does: they leave the alternate screen, turn raw mode off and stop the probe child processes (`kimi web`, `codex app-server`, `claude -p`; SIGTERM, then SIGKILL after 5s), so the terminal is restored and `DANDELION_KIMI_PORT` is freed. If an `l`, `L` or `x` command is running in the foreground at that moment, the signal is forwarded to it first, dandelion waits for it to exit (SIGKILL after 5s) and only then exits; while it runs every key is ignored, including `q`, so a chunk such as `ll` starts only one command. Dandelion then exits with 128 plus the signal number (143 for SIGTERM, 129 for SIGHUP; `q` exits 0), a further SIGTERM or SIGHUP while it shuts down is absorbed (no second shutdown, the exit code stays that of the first signal), and the signal handlers are removed when the dashboard ends. `--once`, `route` and `--json` install no such handlers.
- `npm start -- --once` - Run the dashboard once and exit. `--once --max-age <seconds>` (also when stdout or stdin is not a terminal) prints it from the live dashboard's `snapshot.json` without probing when the snapshot is complete and at most that old, under the same rules as `--json --max-age`; otherwise it probes as plain `--once`. It never writes any state file, and the live dashboard ignores `--max-age`
- `dandelion` - Run the live dashboard from anywhere after `npm link`; `dandelion --once` runs it once and exits
- `dandelion route` (or `npm start -- route`) - Run every probe once and print one line naming the subscription to use right now, such as `claude-opus-5-5 max claude`, then exit; it prints `none` and exits 1 when no provider can be routed, and exits 2 when `routes.json` is bad. It never draws the dashboard, even on a terminal.
- `dandelion route --high` (or `npm start -- route --high`) - Run every probe once and print one line naming the strongest model that still has quota, such as `claude-fable-5-1 max claude-work`, then exit; it prints `none` and exits 1 when no chain entry is available, and exits 2 when `routes.json` is bad. It never draws the dashboard, even on a terminal.
- `dandelion --json` (or `npm start -- --json`) - Run every probe once and print one JSON object on one line, then exit 0; it never draws the dashboard, even on a terminal, and `--json` works anywhere in the arguments unless the first argument is `route`, `run`, `seats`, `help`, `--help` or `-h` (`route`, `help`, `--help` and `-h` ignore it, `seats` prints its own seats JSON instead (see Seats), and `run` passes it on to the launched CLI). The object has `generatedAt`, `providers` (one entry per provider in dashboard order with `id`, `displayName`, `status`, `planLabel`, `eligible`, `windows` of `label`, `kind`, `usedPct`, `resetsAt` and `projectedFullAt` (the ISO time the window is on pace to hit 100% before it resets, the same projection as `→ 100% in …`), `balance`, `snapshotAt`, `note`, `reason` and `fetchedAt`, leaving out whatever a provider does not have), `route` and `routeHigh`, the exact lines `dandelion route` and `dandelion route --high` print, or `none`. With a bad `routes.json`, `route` and `routeHigh` are `null`, `routesError` holds `<path>: <problem>`, the usual `dandelion: routes file ...` line goes to stderr and the exit code is still 0. `--max-age <seconds>` anywhere in the arguments (N a positive integer as a separate argument; `0`, `-5`, `1.5` or a missing value means no cache) answers from the live dashboard's `snapshot.json` instead of probing, with the same rules as `route --max-age`: when the file parses, holds an entry for every provider and every entry was fetched at most N seconds ago, no probe runs and the object is built from those results (`generatedAt` is now, each `fetchedAt` is the entry's own time, and `route`, `routeHigh` and the ineligible providers come from the current routes.json, state file and clock); otherwise it probes exactly as plain `--json`. It reads the state file and never writes it or `snapshot.json`, and never prints tokens. A Waybar custom module that reuses the live dashboard's data when it is at most 10 minutes old: `"custom/dandelion": { "exec": "dandelion --json --max-age 600 | jq -c '{text: .route, tooltip: ([.providers[] | .id + \" \" + .status] | join(\"\\n\"))}'", "return-type": "json", "interval": 300 }`.
- `dandelion --line` (or `npm start -- --line`) - Run every probe once and print one line of plain text for a tmux status bar or shell prompt, then exit 0; it never draws the dashboard and prints no ANSI escape sequence, even on a terminal. The line has one segment per provider that is ok and has at least one usage window, in dashboard order, as `<id> <worst used percent>%` (the highest used percent over its windows, rounded), joined by ` · `, then ` → ` and the exact line `dandelion route` prints, or `none`: `claude 63% · kimi 12% · grok 0% → claude-opus-5-5 max claude`. Providers that are unavailable, failed or without windows (`kilo`, `codex` with an API key) are left out; routing off in the state file does not remove a segment but changes the route part exactly as it does for `route`. With a bad `routes.json` the route part is `routes file error`, the usual `dandelion: routes file ...` line goes to stderr and the exit code is still 0. `--max-age <seconds>` anywhere in the arguments answers from the live dashboard's `snapshot.json` under the same rules as `--json --max-age`; otherwise it probes. `--json` wins when both are given, and `route --line` is plain `route`. It never writes the state, snapshot, view, hidden or history files, installs no signal handlers and never prints tokens. In tmux: `set -g status-right '#(dandelion --line --max-age 600)'`.
- `dandelion --waybar` (or `npm start -- --waybar`) - Run every probe once and print one JSON object on one line for a Waybar custom module with `"return-type": "json"`, then exit 0; it never draws the dashboard, prints no ANSI escape sequence and never prints tokens. Fields: `text` is the route part of `--line`, the exact line `dandelion route` prints, or `none` (`routes file error` with a bad `routes.json`, with the usual `dandelion: routes file ...` line on stderr); `percentage` is the highest rounded used percent over the windows of ok providers (0 when there are none); `class` is `calm` (below 50), `warm` (50-79), `hot` (80-94) or `critical` (95 and up) for that percentage; `tooltip` has one line per ok provider with windows, in dashboard order, as `<id> <worst used percent>%`, joined with `\n`. `--max-age <seconds>` anywhere in the arguments answers from the live dashboard's `snapshot.json` under the same rules as `--line --max-age`; otherwise it probes. `--json` and `--line` win when combined with it. Sample Waybar module: `"custom/dandelion": { "exec": "dandelion --waybar --max-age 600", "return-type": "json", "interval": 300 }`.
- `dandelion run` / `dandelion run --high` - Resolve the route exactly as `route` / `route --high` does (same probes, eligibility state file, `routes.json` and 90% trip), then launch the matching CLI with stdio inherited, as listed under Account token below. `--high` before a literal `--` picks the quality chain and is not passed on; `--max-age <seconds>` before a literal `--` resolves the route from the live dashboard's last snapshot exactly as `route --max-age` does (see Route --max-age), so a fresh snapshot launches at once without waiting on any probe, and it and its value are not passed on (a numeric value such as `0` or `1.5` that is not a positive integer means no cache and is dropped too); every other argument after `run`, and everything after a literal `--`, is appended to the launched command, such as `dandelion run -- -p "hello"`. It prints `none` on stderr and exits 1 without launching when nothing can be routed, prints the `dandelion: routes file …` line on stderr and exits 2 when `routes.json` is bad, prints `dandelion: <command>: command not found` on stderr and exits 127 when the CLI is not on `PATH`, and otherwise exits with the child's exit code. While the child runs, dandelion ignores Ctrl-C (SIGINT) so the child, which receives it from the terminal itself, decides how to end and its exit code (such as 130) is still the one dandelion exits with, and forwards SIGTERM and SIGHUP to the child, exiting with its status (such as 143 or 129) only after it has exited; the handlers are removed when the child exits and exist only for `run`. `route` and `route --high` are unchanged. With `--headless` before any literal `--`, `dandelion run --headless [--seat "<model> [effort] <account>"] --prompt-file <path> --cwd <dir> [--timeout <seconds>] [--high] [--max-age <s>]` launches one seat (or, without `--seat`, the line plain `run` would launch) with nobody at the keyboard instead: argv comes from that CLI's `headless` template in `routes.json`, the prompt file reaches the CLI as its template says, the working directory is `--cwd`, and SIGINT is forwarded too; see Headless launch under Seats. Plain `run` without `--headless` is unchanged.
- `dandelion seats <N>` (or `npm start -- seats <N>`) - Hand out N seats for a swarm, spread across accounts by route's rules and a stricter swarm trip line, and print one `<model> [effort] <account>` line per seat, the same shape `route` prints, then exit 0; `--spread` gives every `--high` rank a seat before any rank gets two, `--why` adds a `# skip <id>: <reason>` line per account that got no seat, and `--json` prints one JSON object for programs. It prints `none` and exits 1 when no account can take a seat, prints `dandelion: seats: <what is wrong>` on stderr and exits 2 for a bad argument, and exits 2 with the usual `dandelion: routes file …` line when `routes.json` is bad. It never draws the dashboard and keeps no state between calls. See Seats.
- `dandelion --help` (also `-h` and `help`) - Print a short usage text to stdout and exit 0 without running any probe. A first argument that is not a known command and does not start with `-`, such as `dandelion rout`, prints `dandelion: unknown command rout` and the usage to stderr and exits 2 without probing; `--json` anywhere still wins. Likewise, when the first argument is not `route`, `run`, `seats`, `help`, `--help` or `-h` and no `--json`, `--line` or `--waybar` is present, any argument starting with `-` other than `--once` and `--max-age` (and the value right after `--max-age`), such as `dandelion --jsno`, prints `dandelion: unknown option --jsno` and the usage to stderr and exits 2 without probing; `route` and `run` arguments are handled as before, and `seats` rejects an option it does not know with its own `dandelion: seats: unknown option …` line and exit 2.
- `npm test` - Run unit tests
- `npm run qa` - Run E2E tests

The app runs once when stdout or stdin is not a terminal, as if `--once` were given.

## Usage history

Every settled round, and every single-panel re-probe, of the live dashboard also replaces `snapshot.json` in the same directory with the current settled results: a JSON array with one entry per provider holding its status, windows and `fetchedAt` (never tokens or auth file contents). It is what `route --max-age` reads (see Route --max-age); it is replaced atomically, a failed write never breaks the dashboard, and `--once`, `--json` and `route` never write it.

Every settled round of the live dashboard appends one sample per usage window of each ok provider (provider, window label, used percent, reset time, timestamp) to `history.json` in the dandelion state dir, next to the eligibility state file (`$XDG_STATE_HOME/dandelion/`, or the directory of `DANDELION_STATE_FILE`; `DANDELION_HISTORY_FILE` names the file directly). Each sample carries the window's position in its provider's list, so windows that share a label are charted separately. Samples older than 30 days are dropped; samples older than a day are thinned to one per window per hour, and at most the newest 40000 are kept, so the full 30 days stay reachable at the default refresh rate. The graph heads each chart with its latest value, marks a drop in usage (a reset) with `↓` (`v` under `NO_COLOR`), says how long the history spans, and says why it is empty for a provider that is probing, unavailable or has no usage windows; on a terminal too short for every window it ends with `… N more windows (enlarge the terminal)`. Each write first re-reads the file and merges in samples another dashboard wrote meanwhile (exact duplicates of the same provider, window position, label and timestamp are dropped), so two dashboards do not erase each other's history. The file is replaced atomically; a missing, corrupt or unwritable file never breaks the dashboard, it just means less history. `--once`, `route` and `route --high` never write it.

Press `g` on a panel to see one chart per window: bars of used percent over time from the first sample to now, a `↓` (`v` with `NO_COLOR`) under each reset, and the time axis in local time. `NO_COLOR` also switches the bars to `#`. `esc`, `q` or `g` returns to the dashboard; `q` on the dashboard quits.

## Route

`route` must be the first argument; later arguments are ignored, except that `--high` anywhere after it switches to the quality chain below and `--why` anywhere after it adds an explanation (see Route --why), and `--max-age <seconds>` answers from the live dashboard's last snapshot instead of probing (see Route --max-age). It routes among `claude`, `claude-work`, `claude-animus`, `claude-deepseek`, `claude-ollama`, `agy`, `kimi`, `grok`, `codex`, `codex-animus`, `cursor`, `junie` and `hermes`, in dashboard order, taking each one that is ok and has at least one usage window. `kilo` is the final balance fallback: it is eligible only when its probe is ok and reports a dollar balance strictly above $10; exactly $10 is rejected. Its balance is not a window and does not compete in evaporation or headroom, and a codex account logged in with an API key has no windows, so it is not routed either.

Each window is rolling (claude session, claude-ollama session, kimi 5h, codex 5h, agy 5h (Claude+GPT · 5h, Gemini · 5h)), weekly (any other label containing "week", grok credits, cursor total, auto and api, junie credits, hermes credits, claude-deepseek spending limit) or other, which route ignores. Junie and Hermes require positive remaining credits before either window rule, so an exhausted credits account cannot win when no other account is available. The plain route leaves out the cursor api window, because its cursor line is `auto`, which draws on the auto pool; `--high` still gates cursor on all its windows. A window's left is 100 minus its used percent, compared without rounding. Probes keep fractional used percents (kimi counters, cursor, codex, grok, junie, hermes, claude-deepseek, claude-ollama), so a kimi 5h counter of 179/200 is 89.5% and does not trip; only text is rounded half up (window rows, the compact view, notifications, `--why` and graph titles), `--json` prints whole-number `usedPct`, and `snapshot.json` and `history.json` store the unrounded value.

1. Evaporation: a weekly window evaporates when it resets after now and before the next local midnight with less than 97% and more than 0% left. If any provider has one, route prints the max line of the provider whose evaporating window has the most left. An account with a spent shared window (100% used, and not a model's own window such as claude's `weekly Fable`) is left out of this rule, since nothing it launches could run; a spent model window does not stop the account's other weekly windows from evaporating.
2. Most headroom: otherwise each provider's binding is the lowest left over its rolling and weekly windows (100 when it has neither), and route prints the standard line of the provider with the highest binding.
3. Kilo balance: only when neither windowed rule can route, route prints Kilo's standard line if Kilo is eligible and its dollar balance is strictly above $10. Exactly $10, a lower balance, a non-dollar balance and a failed or malformed profile do not qualify.

Ties go to the provider earlier in dashboard order.

The trip: before both rules, route skips every tripped account. An account is tripped when any of its rolling windows (claude, claude-work, claude-animus and claude-ollama session, kimi 5h, codex and codex-animus 5h, agy 5h (Claude+GPT · 5h, Gemini · 5h)) is 90% used or more; 90% itself trips, and weekly and other windows never trip. A tripped account's evaporating weekly window is ignored by rule 1 and its binding is ignored by rule 2. It is the same 90% trip `route --high` uses. A panel of an ok, eligible account that is tripped shows `tripped` on the right of its header in the live full view and in `--once`, where `routing off` appears for ineligible panels (which show that and not `tripped`), followed by ` · back <local time>` with exactly the time `route --why` prints for that account (left out when a tripping window has no reset or it has passed); it is coloured like a hot window (plain text under `NO_COLOR`), the compact view is unchanged, and routing and every other output are unaffected. When no account is left once ineligible, unavailable and tripped accounts are skipped, route prints `none` and exits 1.

Limits: an account's entry in `routes.json` may set `limit`, a whole percent from 1 to 100, to keep dandelion from driving that account past it. The shipped file sets `"limit": 75` on `claude-animus`, so Animus's subscription is never routed past 75%; no other account has one. Before both rules and before the `--high` chain, an account is limited while any of its rolling or weekly windows is at or above its limit (the limit itself counts; other windows never do). That covers every such window the account reports, including a model's own window such as claude's `weekly Fable`, not only the windows a route gates on, so a limited account neither evaporates, competes on headroom nor takes any `--high` rank. The 90% trip still applies on top, so a limit above 90 only adds a ceiling on weekly windows. An account without `limit` routes exactly as before, and when every account is limited, tripped, ineligible or unavailable, route prints `none` and exits 1. The check happens when a route is picked: a run launched below the limit can still carry the account past it. A panel of an ok, eligible account that is limited shows `limited` where a tripped one would show `tripped`, followed by ` · back <local time>`, the latest reset among its windows at or over the limit, exactly as `route --why` prints it; `limited` wins when both apply.

Route --max-age: `route --max-age N` and `route --high --max-age N` (N a positive integer of seconds, as a separate argument; anything else, such as `0`, `-5`, `1.5` or a missing value, means no cache) read `snapshot.json` from the dandelion state dir. When it parses, holds an entry for every provider and every entry was fetched at most N seconds ago, they print exactly what `route` / `route --high` would print for those results, with the same exit codes, without running any probe; the ineligible providers come from the current state file, and `routes.json` and the clock are the current ones. `--why` combines with it and explains the same results. A missing, unreadable, corrupt, incomplete or too old file never fails the command: it probes exactly as without the flag. `dandelion --json --max-age N` and `dandelion --once --max-age N` read it the same way (see `--json` and `npm start -- --once`). Plain `route`, `route --high`, `run` and plain `--json` never read the file; `run --max-age N` reads it the same way, and after a literal `--` `--max-age` is an ordinary argument for the launched CLI.

Eligibility: ineligible providers are dropped before both rules and the Kilo balance fallback, so an ineligible provider is never routed, not even by evaporation. In the live dashboard, select a panel with `↑↓/jk` and press space to toggle its routing on or off; an ineligible panel shows `routing off` and keeps showing its usage. Non-routable panels (no usage windows, unavailable or failed) cannot be toggled and flash `not routable (no usage windows)` instead. Kilo is the exception to the window requirement: with an ok dollar balance strictly above $10 it can be toggled even though it has no windows; an unavailable or non-dollar balance cannot be toggled, and a balance at or below $10 is rejected with a message showing the balance and the required floor. Exactly $10 is therefore not routable. The choice is kept in the state file (`DANDELION_STATE_FILE`), a JSON object where `false` marks a provider ineligible; a missing, unreadable or corrupt file makes every provider eligible. The live dashboard also picks up changes another dashboard or a hand edit makes to the state file: it re-reads it at the start of every full refresh round, after every single-panel re-probe settles, and right before `c`, `C`, `l` and `L` act (never on a plain redraw), so the route boxes, the `routing off` label and the copied or launched line match what `dandelion route` would answer. `--once` and `route` read the state file and never write it.

View state: the live dashboard keeps the `s` order and the `t` reset-time mode in `view.json` next to the state file, as `{"sort":"headroom","absoluteResets":true}` (`sort` is `dashboard`, `headroom` or `reset`). It reads the file at start and rewrites it atomically whenever `s` or `t` changes the mode; a missing, unreadable or corrupt file, an unknown `sort` or a non-boolean `absoluteResets` falls back to dashboard order and relative countdowns, and a failed save flashes `view state not saved` and keeps the new mode for the session. `--once`, `route`, `route --high`, `--json` and `run` never read or write it.

Hiding panels: in the live dashboard `h` hides the selected panel and selects the next visible one (the previous one if it was last). Hiding is display only: a hidden provider is still probed and routed exactly as before, and its eligibility is untouched. While panels are hidden a dim `<n> hidden · H to show` line follows the last panel; `H` shows them in place with `hidden` right-aligned in the header, `h` on one unhides it, and `H` again hides them. `↑↓/jk` skip hidden panels while they are not shown. The hidden ids are kept as a JSON array in `hidden.json` next to the state file; a missing, unreadable or corrupt file hides nothing, and a failed save flashes `hidden state not saved` and changes nothing. `--once`, `route` and `route --high` never read or write it.

Another qualifying provider is launched instead, or the command reports `none` without launching anything. Plain `route` does not perform this extra launch check. Route --high: quality first, with no evaporation rule and no headroom comparison. It walks this chain from rank 1 down and prints the line of the first available entry, taken from `routes.json`:

| rank | providers | gating windows | line |
|---|---|---|---|
| 1 | claude, claude-work, claude-animus | `fable`: the Fable weekly window plus session | `high.fable` |
| 2 | codex, codex-animus | (all) | `high.codex` |
| 3 | cursor | (all) | `high.cursor` |
| 4 | claude, claude-work, claude-animus | (all) | `high.opus` |
| 5 | grok | (all) | `high.grok` |
| 6 | agy | (all) | `high.agy` |

An entry with a matcher is gated on the windows whose label contains the matcher in any case, plus every rolling window; a matched window the account does not report counts as 0% used. An (all) entry is gated on every window the provider reports, except the windows another entry of the same provider matches, so the rank 4 entry ignores the Fable window. The 90% trip: an entry is available on an account only when the account is eligible, ok with at least one window, not limited (see Limits), and every gating window is under 90% used; at 90% it pops down to the next entry. Ineligible, unavailable and failed providers are skipped, and `kimi`, `junie`, `hermes`, `kilo`, `claude-deepseek` and `claude-ollama` are never in the chain, so `--high` does not use junie. `--high` does not use hermes. `--high` does not use claude-deepseek. `--high` does not use claude-ollama. `--high` does not use kilo. When both claude accounts are available at one rank, the one with more left (100 minus its highest gating used percent) wins, and a tie goes to `claude`; between `codex` and `codex-animus` at rank 2 the same rule applies and a tie goes to `codex`. When no entry is available it prints `none` and exits 1.

Route --why: `dandelion route --why` and `dandelion route --high --why` print the same route line first, exactly as without `--why`, then at most two explanation lines, and exit with the same code (1 for `none`, 2 with a bad `routes.json`, which still prints nothing on stdout). For `route`, the first line names the rule and its numbers, such as `evaporation: kimi weekly 41% left resets 21:40 before midnight` (reset time in local time), `headroom: claude binding 63% left (claude-work 40%, agy 22%)`, or `balance: kilo $14.15 available; launch requires a fresh balance above $10.00`, and the second lists the skipped accounts by reason, such as `tripped: claude-work (session 92%, back Sat 21:40); ineligible: grok; unavailable: junie, hermes`. An account at its limit is listed first, as `limited: claude-animus (weekly 76%, limit 75%, back Sat 21:40)`, with its most used window at or over the limit and the latest of their resets, and is not listed again as tripped. A Kilo balance at or below the floor is listed with its actual balance and the requirement to be strictly above $10; a failed profile is listed as `kilo (balance unavailable)`. A tripped entry ends with `, back <local time>` (the `t` reset format: weekday and time, or month, day and time when 6 or more days away) when its reset is known and in the future; with several windows at 90% or more it is the latest of their resets, and it is left out when a tripping window has no reset time or the reset has passed. For `route --high`, the first line names the winning rank, entry and account, such as `rank 4 opus on claude: gating 71% used`, and the second says why each higher rank was skipped, such as `skipped: rank 1 fable tripped at 95%; rank 2 codex no open account; rank 3 cursor no open account`, followed by `; limited: …` in the same form as for `route` when a chain account is at its limit (that line is just `limited: …` when no rank was skipped). When nothing is routable the route line is `none` and the explanation still lists what was skipped. Plain `route` and `route --high` print exactly what they always did.

## routes.json

To change a routed model, edit routes.json. The lines `route` and `route --high` print are data in `routes.json` at the repo root; the per-account `limit` is data there too, and so are the optional `swarm`, `lab` and `headless` sections; the rules, the tie order, the `--high` chain order, its providers, the `fable` matcher and the 90% trip stay in code, so the order of keys in the file means nothing. dandelion finds the file from the real path of `src/main.ts` after following symlinks, never from the working directory, so `dandelion route` through an `npm link` symlink reads the checkout's file from any folder. `DANDELION_ROUTES_FILE` points at a different file.

```json
{
  "route": {
    "claude": { "standard": "<line>", "max": "<line>" },
    "claude-work": { "standard": "<line>", "max": "<line>" },
    "claude-animus": { "standard": "<line>", "max": "<line>" },
    "claude-deepseek": { "standard": "<line>", "max": "<line>" },
    "claude-ollama": { "standard": "<line>", "max": "<line>" },
    "agy": { "standard": "<line>", "max": "<line>" },
    "kimi": { "standard": "<line>", "max": "<line>" },
    "grok": { "standard": "<line>", "max": "<line>" },
    "codex": { "standard": "<line>", "max": "<line>" },
    "codex-animus": { "standard": "<line>", "max": "<line>" },
    "cursor": { "standard": "<line>", "max": "<line>" },
    "junie": { "standard": "<line>", "max": "<line>" },
    "hermes": { "standard": "<line>", "max": "<line>" },
    "kilo": { "standard": "<line>", "max": "<line>" }
  },
  "high": { "fable": "<line>", "codex": "<line>", "cursor": "<line>", "opus": "<line>", "grok": "<line>", "agy": "<line>" },
  "swarm": {
    "trip": 80,
    "minLeft": 5,
    "exclude": ["<account id>"],
    "cap": { "<account id>": 3, "default": 2 },
    "burnPerSeatHour": { "<account id>": 12, "default": 10 }
  },
  "lab": { "<model prefix>": "<lab>" },
  "headless": { "<command>": { "before": ["<arg>"], "after": ["<arg>"], "stdin": true } }
}
```

`route` holds one entry per routed provider: `standard` for the headroom rule and the Kilo balance fallback, and `max` for evaporation. Every entry but `kilo` may also hold `limit`, a whole number from 1 to 100, such as `"claude-animus": { "standard": "<line>", "max": "<line>", "limit": 75 }` (see Limits under Route); leave it out for no limit. `high` holds one line per `--high` rank, named `fable`, `codex`, `cursor`, `opus`, `grok` and `agy` for ranks 1 to 6. A line is `<model>` or `<model> <effort>`: one or two words, one space apart. dandelion prints lines as written and never checks model names.

`swarm`, `lab` and `headless` are optional, and so is every key inside `swarm`; a missing one takes its default. `swarm.trip` is the swarm trip line, a whole percent from 50 to 90 (default 80). `swarm.minLeft` is the binding every seat must leave behind, a number from 0 to 100 (default 5). `swarm.exclude` lists account ids that get no seats unless a call names them in `--include` (default none). `swarm.cap` holds the most seats an account may hold, a whole number from 0 to 20 per account id or `default` (default 2, and 1 for `kilo` when it has no key of its own). `swarm.burnPerSeatHour` holds how many percent of its binding one seat is expected to use, a number from 0 to 100 per account id or `default` (default 10). `lab` maps a model-name prefix to a lab name made of `a-z`, `0-9` and `-` (default none). `headless` maps a CLI command (`claude`, `codex`, `cursor-agent`, `agy`, `kimi`, `grok`, `junie`, `hermes` or `kilo`, not an account id) to a template with exactly `before` and `after`, each a list of strings, and `stdin`, `true` or `false` (default none).

`route`, `route --high` and `--once` read and check the whole file once per run; the live dashboard reads it once at start. A bad file is an error, never a fallback: when the file is missing, unreadable or not valid JSON, or when an entry is missing, a key is unknown (including `limit` on `kilo`, a `swarm.cap` key that is not an account id or `default`, and a `headless` key that is not a CLI command), a line is not a non-empty string, a line has the wrong shape, a `limit` is not a whole number from 1 to 100, or a `swarm`, `lab` or `headless` value breaks the rules above, `route` and `route --high` print nothing on stdout, print `dandelion: routes file <path>: <what is wrong>` on stderr and exit 2, even when nothing could be routed. Exit 1 stays reserved for `none`. `--once` prints its dashboard as usual, the same line on stderr, and exits 0. The live dashboard keeps every panel, and both route boxes show `routes file error` over the start of what is wrong.

## Seats

`dandelion seats <N>` hands out a batch of N seats for a swarm: agent slots, each on one account with one model, spread across accounts by route's own rules plus a stricter swarm trip line, so the band from the swarm trip up to route's 90% stays free for your own sessions. brush-cutter is the consumer. `seats` keeps no state: the caller says which seats it already holds with `--held`, and `seats` answers with the full target allocation, held seats included.

```
dandelion seats <N> [--pack | --spread] [--json] [--why] [--max-age <s>]
                    [--held <id>=<n>[,<id>=<n>...]] [--include <id>[,...]] [--exclude <id>[,...]]
                    [--trip <pct>] [--cap <id>=<n>[,...]]
```

`<N>` is the total seats wanted, held ones included, a whole number from 1 to 200. Neither mode flag means `--pack`. `--held` n is 0 to 200 seats the caller holds on that account, `--cap` n (0 to 20, 0 means none) overrides `swarm.cap` for that account, `--trip` (a whole percent from 50 to 90) overrides `swarm.trip`, `--exclude` adds to `swarm.exclude` and `--include` takes accounts out of both. `--held`, `--cap`, `--include` and `--exclude` may repeat, and a later value for the same account wins; the last `--trip` wins. Both mode flags, a missing or bad `N`, a second `N`, an unknown flag, a flag without its value, an unknown account id or an out-of-range value prints `dandelion: seats: <what is wrong>` on stderr and exits 2 before anything is probed. Probing works as for `route`: every probe runs once, or `--max-age <seconds>` answers from `snapshot.json` under the rules of `route --max-age` (a value that is not a positive integer means no cache). The eligibility state file, `limit` and `routes.json` apply exactly as they do for `route`, and a bad `routes.json` prints the usual `dandelion: routes file …` line, nothing on stdout, and exits 2.

An account gets no seat, for the first of these reasons that applies (the reason names are the `skip.reason` values of `--json`):

1. `excluded`: it is in `swarm.exclude` or `--exclude` and not in `--include`. The shipped file excludes the work accounts `claude-work`, `claude-animus` and `codex-animus`.
2. `ineligible`: routing is off for it in the state file.
3. `unavailable`: its probe is not ok, or it has no usage windows route reads (kilo needs no windows, only an ok probe).
4. `limited`: it is at its route `limit` (see Limits under Route).
5. `tripped`: one of its rolling windows is at or above the swarm trip; the trip itself trips, like route's 90%.
6. `no-headless`: its CLI command has no `headless` template in `routes.json`, so `run --headless` could not launch it.
7. `not-in-chain`, with `--spread` only: it is in no `--high` chain entry, or every entry it is in has a gating window at or above the swarm trip.
8. `spent`: not even one seat fits under the headroom rule below, or its cap is 0.
9. `balance`, kilo only: its dollar balance is not strictly above $10, the rule route uses.

Headroom rule: an account's binding is route's binding (the lowest left over its rolling and weekly windows, 100 when it has neither), its burn is `swarm.burnPerSeatHour` for it, else `default`, and its cap is `--cap`, else `swarm.cap` for it, else `swarm.cap.default`. It can hold k seats while binding minus k times burn is at least `swarm.minLeft` and k is at most its cap. The score of its next seat is binding minus (seats it already has plus 1) times burn, and ties go to dashboard order.

Allocation:

1. Held seats are kept first, so asking again on an unchanged snapshot does not churn: each account keeps the smaller of its `--held` count and what it is allowed now (0 when it is skipped). When the kept seats add up to more than N, they are dropped one at a time from the account whose last kept seat scores lowest, kilo first, and on a tie from the account later in dashboard order.
2. `--pack`: accounts with a weekly window route's evaporation rule would take (it resets before the next local midnight with less than 97% and more than 0% left, and the account's shared windows are not spent) are served first, the one whose window has the most left first, each up to its allowance, with that account's `max` line. The remaining seats go one at a time to the highest score with the `standard` line. Kilo gets seats (its cap is `swarm.cap.kilo`, 1 unless set) with its `standard` line only when no windowed account can take another.
3. `--spread`: every `--high` rank (`fable`, `codex`, `cursor`, `opus`, `grok`, `agy`) is available on an account that passes the rules above and whose gating windows for that entry, chosen as `route --high` chooses them, are all under the swarm trip. Seats go in rounds: each rank, in chain order, that still has an available account with room gets one seat with its `high` line on the account whose next seat scores highest, so every rank gets a seat before any gets two, until N seats are given or no rank can take one. Caps and the headroom rule are per account across ranks. A kept held seat takes the highest rank its account is available for and counts as that rank's turn.
4. Kept seats keep the line their account would get now: in `--pack` the `max` line on an evaporating account and the `standard` line otherwise, and in `--spread` the line of their rank.

Plain output is one `<model> [effort] <account>` line per seat, kept seats first and then in allocation order, so `dandelion run --headless --seat "<line>"` launches any of them as printed. With `--why`, one `# skip <id>: <text>` line follows for every skipped account in dashboard order, such as `# skip claude: tripped at 83%, back Sat 21:40` (local time, in the `t` reset format; the `back` part is left out when the reset is unknown or past). The texts are `excluded`, `routing off`, `unavailable` or `no usage windows`, `limited at 76% (limit 75%)`, `tripped at 83%`, `no headless template for <command>`, `not in the --high chain` or `no --high rank under 80%`, `cap 0` or `spent: 12% left, one seat needs 15%`, and `balance $9.00, needs above $10.00` or `balance unavailable`. No seat at all prints `none` and exits 1; otherwise the exit code is 0.

`--json` prints one JSON object on one line, whenever `routes.json` is good, and exits 1 when `seats` is empty, else 0:

```json
{
  "generatedAt": "2026-10-28T23:10:00.000Z",
  "mode": "pack",
  "requested": 24,
  "trip": 80,
  "seats": [
    { "account": "codex", "line": "<model> high codex", "model": "<model>", "effort": "high",
      "command": "codex", "lab": "openai", "kind": "headroom", "rank": null, "rankName": null, "held": true }
  ],
  "accounts": [
    { "id": "codex", "command": "codex", "cap": 3, "held": 2, "target": 3, "score": 41.5,
      "evaporating": false, "balance": null,
      "skip": null,
      "windows": [ { "label": "5h", "kind": "rolling", "usedPct": 30, "resetsAt": "2026-10-29T01:20:00.000Z" } ] }
  ]
}
```

- `generatedAt` is now, `mode` is `pack` or `spread`, `requested` is N and `trip` is the swarm trip in force.
- Each seat has `account`, `line` (exactly the plain line), `model`, `effort` (`null` when the line has none), `command` (the CLI `run --headless` starts), `lab`, `kind` (`evaporating`, `headroom`, `balance` or `chain`), `rank` (1 to 6) and `rankName` (`fable`, `codex`, `cursor`, `opus`, `grok` or `agy`), both set only for `chain`, and `held`, true for a kept held seat. A seat's lab comes from its model, not its CLI (claude-deepseek runs the claude CLI on a DeepSeek model): the `lab` value of the longest model-name prefix in `routes.json` that matches, else `unknown`.
- `accounts` has one entry for every routed account in dashboard order, kilo included: `id`, `command`, `cap` (the cap in force), `held` (its `--held` count), `target` (the seats it got), `score` (its binding, or `null` for an account with no usage windows, kilo always), `evaporating`, `balance` (kilo's dollar balance, else `null`), `skip` (`null`, or `{ "reason": "<one of the reasons above>", "text": "<the --why text>", "backAt": "<ISO>" }` where `backAt` is the latest reset of the limiting or tripping windows, or `null`) and `windows` (every window it reports, with `label`, `kind`, `usedPct` rounded and `resetsAt`, as in `dandelion --json`).

Headless launch: `dandelion run --headless` starts one seat's CLI with a prompt file in a given directory, without a terminal; brush-cutter runs every agent turn through it and never starts an agent CLI itself.

```
dandelion run --headless [--seat "<model> [effort] <account>"] --prompt-file <path> --cwd <dir> [--timeout <seconds>] [--high] [--max-age <s>]
```

- With `--seat` there is no probing or routing: that line, exactly as `seats` prints it, is launched. Without it the route is resolved as plain `run` resolves it, `--high`, `--max-age`, the eligibility state file and the Kilo launch freshness check included.
- The command and the model and effort flags are the ones `dandelion run` uses for the account (see Account token under Route). argv is `<command> ...before ...model and effort flags ...after` from the command's `headless` template in `routes.json`. `before` exists for subcommands (`codex exec`, `kilo run`). In `after`, `{prompt}` is replaced by the prompt file's contents and `{promptFile}` by its absolute path, wherever they appear in an argument and taken literally. With `"stdin": true` the prompt file is the CLI's stdin; otherwise its stdin is empty (`/dev/null`).
- The CLI runs in `--cwd` with the current environment plus the account's (`CLAUDE_CONFIG_DIR` or `CODEX_HOME`, as for `dandelion run`) and `PWD` set to `--cwd`, since some CLIs (kilo) take their working directory from `PWD` rather than from the process. Its stdout and stderr pass through unchanged.
- A `--seat` on kilo runs another `kilo profile --json` first; at or below $10 it prints `dandelion: kilo balance at or below $10` on stderr and exits 1 without launching.
- `--timeout <seconds>` (a positive whole number) sends SIGTERM when the time is up, SIGKILL 5s later if the CLI is still running, and exits 124 once it has exited. While the CLI runs, SIGTERM, SIGHUP and SIGINT are forwarded to it and dandelion exits with its status only after it has exited; the handlers exist only while it runs.
- Exit codes: the CLI's own exit code (128 plus the signal number when a signal ended it); 124 on `--timeout`; 127 with `dandelion: <command>: command not found` when the CLI is not on `PATH`; 1 with `none` when nothing routes, or for the kilo check; 2 for a usage error, a prompt file that cannot be read, a `--cwd` that is not a directory, an unknown account, a `--seat` that is not `<model> [effort] <account>`, a bad `routes.json` (the usual `dandelion: routes file …` line), a command without a template (`dandelion: run: no headless template for <command>`), or a `{prompt}` template with a prompt file over 120000 bytes (`dandelion: run: prompt too long for <command>; use a stdin or {promptFile} template`). Every other exit-2 line starts `dandelion: run: `, and an argument `run --headless` does not know, a literal `--` included, is a usage error.

The shipped `headless` section holds only templates proven on this machine (2026-10-29) by launching each account's `standard` line headless in a fresh git repo with a prompt to create `ok.txt`; a template ships only when the exit code was 0 and `ok.txt` said `ok`:

- claude: `-p --output-format json --dangerously-skip-permissions` after the model flags, with the prompt on stdin.
- codex: `exec` before the model flags and `--dangerously-bypass-approvals-and-sandbox -` after them, with the prompt on stdin (`-` makes `codex exec` read it).
- agy: `--dangerously-skip-permissions -p {prompt}`; agy's `-p` takes the prompt as its value and does not read stdin.
- kimi: `-p {prompt}`; kimi's prompt mode edits files by itself and refuses `--yolo` and `--auto`.
- grok: `--always-approve --output-format plain --prompt-file {promptFile}`.

Left out, so those accounts get the `no-headless` skip until a template is proven: `cursor-agent` (the cursor account was at its usage limit, so no run could succeed; the candidate is `-p --force --output-format text {prompt}`), `junie` (its balance was spent; candidate `--skip-update-check {prompt}`), `hermes` (its Nous Portal credits were exhausted; candidate `--yolo -z {prompt}`) and `kilo` (`kilo run` answers `Model not found` for the model id in the shipped `route.kilo` lines; `run` before and `--auto {prompt}` after worked when the same model was written with kilo's own prefix, as `kilo/deepseek/...`).

## Env-var Ledger

- `DANDELION_KILO_REFERENCE` - A legacy gauge-only display setting, never a usage window, allowance or routing threshold. It has no effect on the strict $10 routing eligibility check. The current Kilo probe and panel are balance-only: they ignore this setting and any legacy cached reference, so no gauge or usage percentage is synthesized from the balance.
- `DANDELION_CLAUDE_DEEPSEEK_CONFIG_DIR` - The deepseek claude config dir. Defaults to `~/.claude-deepseek` when unset or empty. The probe reads `settings.json` there for the OpenRouter token and `dandelion run` passes the dir to claude as `CLAUDE_CONFIG_DIR`. When it is not a directory, or the token is missing, the panel says `no deepseek config — CLAUDE_CONFIG_DIR=~/.claude-deepseek claude`. The token is never printed.
- `DANDELION_CLAUDE_OLLAMA_CONFIG_DIR` - The Ollama claude config dir. Defaults to `~/.claude-ollama` when unset or empty. `dandelion run` passes it to claude as `CLAUDE_CONFIG_DIR`, so its `settings.json` should point `ANTHROPIC_BASE_URL` at `https://ollama.com` with an Ollama API key as `ANTHROPIC_AUTH_TOKEN`; the probe reads only the `ollama-session` cookie file there. When it is not a directory the panel says `no ollama config — CLAUDE_CONFIG_DIR=~/.claude-ollama claude`. The cookie is never printed.

It follows the same rules as `DANDELION_CLAUDE_STATUS_URL`: `status: <status.description>` directly under the panel header, warm for `minor`, hot for any other indicator except `none`, plain under `NO_COLOR`, nothing on any failure. Display only: routing, the route boxes, `route`, `route --high`, `run`, `--once`, `--json`, `--line`, `--waybar` and notifications never fetch it.

Writes go to a temp file in the same directory, then rename over it. `hidden.json`, the panels the live dashboard hides with `h`, and `view.json`, the `s` order and `t` mode, live in the same directory and is written the same way. `snapshot.json`, the settled results the live dashboard saves for `route --max-age`, lives there too.

- `DANDELION_NOTIFY` - When set to a non-empty value, the live dashboard sends a desktop notification through `notify-send` after a probe settles: when a window crosses 80% or 95% used, when an account that had a rolling window at 90% or more has none left (a recovered account), naming each window that dropped below 90%, and when a weekly window starts to evaporate (resets before local midnight with less than 97% and more than 0% left), with the time left, and when a weekly window resets and its usage drops (`claude weekly reset: 3% used`). The first round only sets a baseline, and the same event for the same provider, window and reset period fires once per session. A missing `notify-send` is ignored. Notifications that come due while an `x`, `l` or `L` command runs in the foreground are held back and sent once, after it exits. `--once` and `route` never notify. Off by default.
- `DANDELION_NOTIFY_THRESHOLDS` - Comma-separated whole percentages from 1 to 100, such as `50,90`, that replace 80 and 95 as the usage levels `DANDELION_NOTIFY` announces. Whitespace is ignored and invalid entries are dropped; unset, empty or all-invalid keeps `80,95`. When one probe crosses several thresholds, only the highest is announced, and each threshold fires once per window and reset period. Other notifications and the fleet summary are unaffected.
- `DANDELION_DISABLE` - A comma-separated list of provider ids (`claude`, `claude-work`, `claude-animus`, `claude-deepseek`, `claude-ollama`, `agy`, `kimi`, `grok`, `codex`, `codex-animus`, `cursor`, `junie`, `hermes`, `kilo`) to switch off entirely; whitespace around the ids is ignored. Unlike `h`, which only hides a panel that is still probed and routed, a disabled provider is never probed: no CLI is started, no file is read and no request is made. It has no panel in the live dashboard or `--once`, is absent from `--json` `providers`, `--line` and `snapshot.json`, and routing treats it as unavailable, with the routing rules, the `--high` chain and the 90% trip unchanged. `route --max-age`, `run --max-age`, `--json --max-age` and `--line --max-age` count a snapshot as complete when it has a fresh entry for every enabled provider. An unknown id prints `dandelion: DANDELION_DISABLE: unknown provider <id>` once on stderr and is otherwise ignored. Unset or empty disables nothing.
